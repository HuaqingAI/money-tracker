## Story

As a 开发团队,
I want 应用认证契约被正式写入架构文档并落地验证中间件,
so that Epic 2 后续所有受保护 API 都遵循统一的 token 来源与验签规则，不再出现 Story 1.2 / Story 1.8 之间 token 来源不一致的情况。

## Acceptance Criteria

1. `_bmad-output/planning-artifacts/architecture.md` 存在清晰的“应用认证契约”章节，并覆盖 token 来源、验签位置、用户识别、Supabase Auth 角色、测试要求。
2. 认证契约明确：业务 API 即 `/api/**` 除 `/api/auth/**` 外，统一使用应用自签 JWT；`userId` 必须来自 JWT `sub`，不得信任客户端 body/query 传入的 userId。
3. 在实际后端应用 `apps/api` 中新增根级 `middleware.ts`，通过 matcher 统一拦截受保护 API 路由：`/api/**` 除 `/api/auth/**` 与 `/api/health` 外均需 token。
4. 提供 canonical helper `getAuthenticatedUser(request)` 供业务 handler 获取已验证用户；现有 `requireAuthenticatedUser(request)` 可保留为兼容别名，但新代码应使用 `getAuthenticatedUser`。
5. 既有受保护路由完成合规检查或迁移，至少覆盖：`user/profile`、`user/delete-account`、`billing/transactions`、`billing/pending-confirmations`、`dashboard/monthly-summary`、`analytics/*`、`admin/csv-rules`。
6. 单元测试覆盖三种认证分支：无 token、过期 token、有效 token；同时覆盖 `/api/auth/**` 与 `/api/health` 不被拦截。
7. 所有认证失败响应保持统一 API 格式：`{ success: false, error: { code: "AUTH_UNAUTHORIZED", message: string } }`，HTTP status 为 401。

## Dev Notes

### 当前实现基线

- 后端实际应用目录是 `apps/api`，不是 `apps/backend`。任何新增中间件、测试、helper 都应落在 `apps/api`。
- 当前没有根级 `apps/api/middleware.ts`；受保护 API 主要在各 route handler 内调用 `requireAuthenticatedUser(request)`。
- 当前已有 `apps/api/lib/middleware/require-authenticated-user.ts`，负责从 `Authorization: Bearer <token>` 提取 token、验证应用自签 JWT、构造 Supabase `User` 形状，并在非 app token 时 fallback 到 `getSupabaseAdmin().auth.getUser(accessToken)`。
- 当前已有测试 `apps/api/lib/middleware/require-authenticated-user.test.ts`，覆盖 app token、Supabase fallback、篡改 token、过期 token。新增中间件测试应复用这个方向，不要新建第二套 JWT 解析逻辑。
- 当前 auth service 在 `apps/api/lib/auth/service.ts` 签发 access token，payload 含 `sub`、`phone`、`authMethod`、`needsOnboarding`，但未显式包含 `type: "access"`。架构章节若要求 `type`，本 story 应补齐或把架构改为与实现一致；推荐补齐 `type`，因为它能防止 refresh token 被误用为 access token。

### Story 1.2 / 1.8 经验

- Story 1.2 已落地 OTP、微信 callback contract、refresh、移动端 auth-store，并采用应用自签 JWT 作为登录态。
- Story 1.8 初版曾按 Supabase Auth token 设计资料 API，后续 post-review 已修正为兼容应用自签 JWT；这正是本 story 要正式收口的跨 story 契约问题。
- Story 1.8 已暴露真实设备 API URL 与本地 `localhost` 的问题；本 story 不改 mobile URL，但所有登录后 API 写入类 story 后续必须记录真机或等效网络验证证据。

### 认证契约细则

- Token 来源：移动端/API 客户端传 `Authorization: Bearer <appAccessToken>`。
- Access token TTL：沿用 `packages/shared/constants/auth.ts` 的 15min。
- Refresh token TTL：沿用 `packages/shared/constants/auth.ts` 的 7 天，并继续只通过 `POST /api/auth/refresh` 使用。
- 用户识别：业务逻辑只能使用 `getAuthenticatedUser(request).user.id` 或兼容别名返回的 `user.id`。
- 禁止事项：不要从 request body、query string 或 header 中读取 `userId` 作为授权身份。
- Supabase Auth 角色：OAuth/OTP 签发源和历史 fallback；新业务 API 不应依赖 Supabase access token 作为正式契约。
- RLS 注意：当前 `apps/api` 多数路径使用 Supabase admin/service 侧能力，不能把 RLS 当作唯一保护；API 层仍必须先完成用户身份识别与 user_id 过滤。

### 最新技术信息

- 当前项目依赖 `next: ~15.3.0`，因此本 story 使用 `middleware.ts` 文件约定。Next.js 官方文档说明 Next 16 起该约定已更名为 `proxy.ts`；升级到 Next 16 时再运行官方 codemod 或手动迁移，不要在当前依赖下提前创建 `proxy.ts`。
- Next.js 官方文档说明 middleware/proxy 位于 app 或 pages 同级，并通过 `matcher` 控制匹配路径；本 story 的 matcher 应只命中需要保护的 API 路径。
- Supabase 官方文档说明 `auth.getUser(jwt)` 会向 Auth 服务发请求并返回可信 user，可用于 fallback 验证；但本项目正式契约是应用自签 JWT，因此 fallback 只能作为兼容路径。

### 测试要求

- 新增中间件测试必须断言响应 JSON，而不是只断言 status。
- helper 测试必须覆盖 app-issued token 优先，不应在有效 app token 时调用 Supabase `auth.getUser`。
- 过期 app token 不应被误判为有效；若 fallback 到 Supabase，也必须最终返回统一 `AUTH_UNAUTHORIZED`。
- 测试使用 Vitest，沿用现有 `vi.hoisted` + `vi.mock` 模式。
- 不引入新依赖。

### 回归风险

- 如果中间件直接查询 repository，会增加所有受保护 API 的额外 IO，并且和 handler helper 重复；中间件保持轻量，handler 继续通过 helper 获取完整 user。
- 如果一次性把所有 route 的 `requireAuthenticatedUser` 改名为 `getAuthenticatedUser`，可能产生大面积无收益 diff；推荐导出新 helper 并逐步迁移。
- 如果 middleware matcher 把 `/api/auth/refresh` 拦住，过期 access token 将无法刷新，移动端冷启动会被迫退出登录。
- 如果 `/api/health` 被拦住，部署健康检查会失败。
