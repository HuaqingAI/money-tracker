## 1. Epic 回顾

### 1.1 Epic 目标

Epic 1 的目标是交付 MVP 首次体验闭环：用户从欢迎页、注册、通知授权、账单导入，到 AI 分类确认、Dashboard、月报和基础账户合规，完成“零输入财务管家”的第一条可用路径。

覆盖范围：

- FR1：Android 通知捕获
- FR2：CSV 账单导入
- FR3：AI 自动分类与确认
- FR4：Dashboard 首页
- FR5：月度报表
- FR6：用户注册与认证
- FR19：基础账户与 PIPL 合规

### 1.2 交付结果概览

基于 `_bmad-output/implementation-artifacts/sprint-status.yaml`：

- Epic 1：`done`

- Epic 1 retrospective：本次回顾前为 `optional`

基于 story 文件自身状态：

- `1-2`、`1-3`、`1-4`、`1-5`、`1-7`、`1-8`：`done`
- `1-6-dashboard-home.md`：仍为 `review`

## 2. 成功之处

### 2.1 首次体验主链路成型

Epic 1 已经把 MVP 核心体验串起来：

- 注册与认证：OTP、微信 callback contract、refresh token、路由守卫、隐私同意记录
- Android 捕获：规则分发、结构化解析、去重、上传入口、厂商引导
- CSV 导入：编码回退、规则热更新、幂等、去重、导入摘要、移动端文件选择
- AI 分类：后端触发、provider fallback、分类确认、拒绝、改分类、反馈规则
- Dashboard：月度概览、待确认入口、最近交易、AI Spotlight、空态和错误态
- 月报：支出聚合、分类分布、趋势查询、月份切换、缓存作用域
- 账户合规：资料编辑、隐私入口、退出登录、删除账户、PIPL 删除流程

### 2.2 Review 质量明显提升

Epic 1 的 review 抓到了 59 个 patch 级问题，覆盖安全、数据一致性、用户隔离、错误格式、幂等、并发、缓存作用域、真机 API 地址和设计保真度。

典型高价值修复：

- Story 1.2 修复隐私协议绕过、过期 session 被信任、非法 JSON 不走统一错误格式、refresh token 非原子轮换
- Story 1.3 修复捕获接口未鉴权、上传失败静默成功、厂商检测硬编码、无效 regex 中断解析、收入通知被当支出
- Story 1.4 修复持久化失败假成功、CSV 规则非原子更新、并发去重窗口、账单交易号缺失导致误去重
- Story 1.5 修复导入后分类范围过大、同步 AI 阻塞导入响应、未分类交易可确认、fallback 状态不持久
- Story 1.7 修复月报缓存缺少用户作用域、趋势 fallback、空预聚合、收入/结余占位误导
- Story 1.8 修复受保护页面路由守卫、服务端错误泄露、app JWT 与 Supabase Auth 假设不一致、真机 `localhost` 问题

### 2.3 架构约束被持续复用

多个 story 都延续了同一套工程约束：

- API 统一 `ApiResponse<T>`
- 金额使用 cents 整数
- 数据库 snake_case，API/mobile camelCase
- shared 放契约、schema、纯工具
- mobile 与 api 通过 HTTP 和 shared contract 协作
- 测试 co-located
- 数据库变更通过 Supabase migration

这说明 Epic 0 的基础设施投入在 Epic 1 中开始产生复用价值。

### 2.4 功能 story 没有大规模反向改造底座

Epic 0 回顾强调“功能 story 不顺手升级基础设施版本”。Epic 1 基本遵守了这个原则。新增依赖主要服务于明确功能需求，例如 CSV 文件选择；多数修改集中在 shared/API/mobile 的业务边界内。

## 3. 问题与阻力

### 3.1 状态可信度仍然不足

最明显的问题是状态源不一致：

- sprint-status 认为 `1-1` 和 `1-6` 均完成
- `1-1` story 文件仍是 `ready-for-dev`，任务与 Dev Agent Record 未收口
- `1-6` story 文件仍是 `review`，且 Review Findings 仍有未勾选 patch

这不是单纯文档瑕疵。它会影响 retro、下一 Epic 准备、验收判断和后续 agent 接手。

### 3.2 跨 story 契约不够显式

多个问题来自相邻 story 对同一事实的不同假设：

- Story 1.2 落地应用自签 JWT，Story 1.8 初版仍按 Supabase Auth token 设计资料 API
- Story 1.3 和 Story 1.6 都暴露“收入/支出方向”缺失导致的口径风险
- Story 1.6 Dashboard 纳入 `pending_confirmation`，Story 1.7 月报只统计 `confirmed`，pending 在报表中的产品口径未统一
- Story 1.5 的导入后分类曾依赖不稳定的后台触发模型，处理页口径也曾误用待确认数量判断识别进度

这些问题说明单个 story 内的 AC 不足以约束跨功能契约。Epic 2 会更依赖交易模型，因此必须前置解决。

### 3.3 高保真设计到 AC 的映射仍有漏项

Story 1.8 的 post-review 明确记录：AC 只写“昵称/头像”，但高保真原型还有性别/生日，导致初版没有进入 schema、API payload 和 UI 保存状态。

这不是账户页独有风险。Epic 2 的交易详情、手动记账、分类规则管理都会有字段密度更高的页面。如果不建立“原型字段逐项映射”检查，类似漏项会重复出现。

### 3.4 移动端真机验收还没有成为硬门槛

Story 1.8 暴露资料保存真机访问 `localhost` 的问题。该问题单元测试和本地 API 测试很难覆盖，只能通过真机或等效网络路径发现。

Epic 2 涉及更多移动端输入、筛选、详情、手动补录和可能的 iOS 替代路径，真机验收缺失会放大风险。

### 3.5 Windows 环境问题仍在干扰验证

Epic 0 回顾提到 Windows 本地环境不是稳定基线。Epic 1 仍出现：

- `rg` 被拒绝执行
- worktree 缺少 `node_modules`
- Next standalone traced files 在 Windows symlink 权限下失败
- detached HEAD / worktree 路径反复需要人工校正

这些问题没有阻止交付，但会降低验证效率和状态可信度。

## 5. 技术债与延后事项

当前明确延后事项：

1. 认证来源统一需要上层架构决策  
   Story 1.2 已实现应用自签 JWT，后续应明确移动端业务 API 使用哪种 token、服务端如何验签、何时落 Supabase Auth。

2. 头像长期持久化仍需 Supabase Storage 或替代方案  
   当前 MVP 保存本地 URI，跨设备、重装恢复、访问控制和删除账户清理仍未解决。

3. 高保真原型字段必须进入 story AC / schema / API payload / UI 状态审查  
   Story 1.8 已经证明只看 AC 会漏掉原型字段。

4. 真机验收路径需要纳入移动端 Definition of Done  
   登录后业务 API 保存类操作必须覆盖真机或等效网络路径。

5. 月报是否纳入待确认账单仍需产品口径  
   pending 交易是真实消费，但分类未确认；在月报、Dashboard、交易列表里的呈现需要统一。

### 6.2 Epic 2 主要风险

1. 交易方向模型不足  
   当前交易方向字段不稳定，已经在通知捕获、Dashboard、月报里产生风险。Epic 2 的交易列表、详情、手动记账必须明确收入、支出、退款、关闭交易的处理规则。

2. pending 口径未统一  
   Dashboard 与月报口径不同。交易列表需要决定 pending 是否展示、如何标记、是否进入筛选与汇总。

3. 认证契约未正式写入架构补丁  
   如果 Epic 2 的新接口继续各自假设 token 来源，会重复 Story 1.8 的问题。

4. 分类规则闭环复杂度上升  
   Story 1.5 已有用户规则，但 Epic 2 的规则管理会把它变成用户可见能力，需要补齐规则优先级、解释、禁用、编辑和冲突处理。

5. 移动端输入路径增多  
   手动记账、语音、截图、iOS 替代方案都更依赖真机或平台能力，单元测试不足以证明可用。

## 9. 关键经验

1. Review 是 Epic 1 最大质量杠杆，但它不能替代完整验收输入。  
   代码风险能靠 review 抓住，原型字段和真机路径必须靠 checklist 和验收纪律补齐。

2. 跨 story 契约要显式写下来。  
   认证、交易状态、交易方向、pending 口径、分类规则不是单个 story 的局部实现，必须作为共享契约管理。

3. sprint-status 不是事实本身。  
   状态文件、story 文档、review findings、代码和验证记录必须一致，才适合作为下一 Epic 的输入。

4. MVP 可以接受局部能力简化，但不能让简化变成隐含假设。  
   头像本地 URI、开发态 OTP、未接原生通知监听、AI fallback 进程内状态都可以作为 MVP 选择，但需要明确后续边界。
