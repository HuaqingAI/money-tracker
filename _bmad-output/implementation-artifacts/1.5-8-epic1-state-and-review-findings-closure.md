## Story

## Acceptance Criteria

1. 核实 Story 1-1 实际代码交付状态，并让 `_bmad-output/implementation-artifacts/1-1-welcome-and-onboarding.md`、代码、测试记录与 `_bmad-output/implementation-artifacts/sprint-status.yaml` 一致：若代码已完成，则补齐 Tasks 勾选、Dev Agent Record、Verification、File List、Change Log，并将 Story 文件状态改为 `done`；若未完成，则将 sprint-status 中 `1-1-welcome-and-onboarding` 从 `done` 回滚到准确状态并登记补齐计划。
2. 核实并关闭 Story 1-6 的四个 review findings：Dashboard loading/error gate、完整数据态缺少通知权限重入口、正数收入月份被计为支出、嵌套 `.env.local` 未忽略。每项必须在 `_bmad-output/implementation-artifacts/1-6-dashboard-home.md` 的 Review Findings 中勾选为已处理，或显式 triage 到后续 story 并写明原因。
3. Story 1-6 的 Dashboard loading/error 处理必须允许 summary 与 recent transactions 两个数据块独立成功展示：一个 query 失败时不得把另一个已成功数据块替换成整页错误；仅两个核心数据块都没有可展示数据且存在错误时才展示整页错误兜底。
4. Story 1-6 的完整数据态必须保留重新进入通知权限页的入口；该入口可放在 Dashboard CTA 区、FAB 菜单或专门状态卡中，但不能只出现在 Empty State。
5. Story 1-6 的支出聚合必须遵循 `architecture.md`「交易方向与状态口径」：`direction = income` 与 `direction = refund` 不进入"本月支出"；在 direction 字段尚未完全落地或历史数据缺失时，不得用"所有金额均为正数"推断整月都是支出，必须有可测试的兼容策略并记录边界。
6. `.gitignore` 必须忽略根目录、应用目录及任意嵌套目录中的 `.env.local` / `.env.*.local`，同时不误忽略 `.env.example`；完成后用 git 状态或针对性检查证明嵌套环境文件不会被纳入版本控制。
7. `_bmad-output/implementation-artifacts/epic-1-retro-2026-04-29.md` 的行动项 #1、#2 必须从 pending 语义收口为 closed 或 explicitly triaged，并记录对应 story / commit / 验证证据。
8. 完成后同步 `_bmad-output/implementation-artifacts/sprint-status.yaml`：`1-1-welcome-and-onboarding`、`1-6-dashboard-home`、`1.5-8-epic1-state-and-review-findings-closure` 与各自 story 文件状态一致；不得出现 sprint-status 标 `done` 而 story 文件仍为 `ready-for-dev` 或 `review`。
9. 验证必须覆盖受影响范围：Story 1-1 onboarding content 测试、Story 1-6 dashboard service/API/mobile 相关测试、TypeScript/lint/build。若 Windows Next standalone symlink 权限导致 root build 阻塞，必须记录失败阶段并补跑 `pnpm --filter api exec tsc --noEmit` 与 `pnpm --filter mobile exec tsc --noEmit`。

- Story 1-1 的代码看起来已经存在：`apps/mobile/app/index.tsx` 已重定向到 `AUTH_ROUTES.welcome`，`apps/mobile/app/(auth)/welcome.tsx` 使用 `WelcomeScreen`，`apps/mobile/screens/onboarding/content.test.ts` 已覆盖三屏引导和路由目标。但 Story 1-1 文件的任务、Verification、File List 仍未收口。
- Story 1-6 当前 Review Findings 仍有 4 项未勾选，且当前代码中仍可看到对应入口：`dashboard.tsx` 使用整页 `hasError` gate，完整数据态只有报表/导入 CTA；`.gitignore` 只忽略根级 `/.env.local` 与 `apps/*/.env`；`dashboard-service.ts` 仍存在 `shouldTreatPositiveAmountsAsExpenses()`。

### 架构约束

- API 响应保持统一 `ApiResponse<T>`，不得为本收口 story 改动 Dashboard API contract。
- 金额继续用 cents 整数；支出聚合不得用浮点数。
- 数据库变更必须通过 Supabase migration。本 Story 以关闭状态和现有 findings 为主；若发现必须补 direction 字段，先确认 Story 1.5.2 是否已经落地，避免重复 migration。
- Dashboard / 月报 / 交易列表 / 手动记账的交易方向与 pending 口径必须遵循 `architecture.md`「交易方向与状态口径」。本 Story 只处理 Story 1-6 的已知 bug，不扩大到交易列表或手动记账。
- UI 修复不要引入新依赖；Dashboard 当前没有 lucide 图标依赖，不为通知权限入口新增图标库。
- 不要回滚 Epic 1 的已完成代码。若发现 Story 1-1 实际未完成，回滚的是状态语义，不是代码。

### 实现指引

- Dashboard error gate 推荐改为块级渲染：
  - summary 初次加载时展示 summary skeleton；
  - summary 有旧数据但 refetch 失败时保留旧数据并展示轻量错误提示；
  - recent transactions 失败时仅隐藏/替换最近交易区块，不覆盖 summary；
  - 只有 summary 和 recent transactions 都没有数据且至少一个失败时，才展示整页错误兜底。
- 通知权限重入口可以放在 `ActionSection()`，与"查看完整报表"、"补充更多账单数据"并列；文案应延续 Story 1.6 Empty State："开启通知读取 / 消费到账自动识别，不用动手"。
- `.gitignore` 建议新增：
  - `.env.local`
  - `.env.*.local`
  - `**/.env.local`
  - `**/.env.*.local`
  并保留 `.env.example` 当前可跟踪状态。
- Story 1-1 文档补齐时，不要伪造未运行的验证命令。实际运行失败就如实记录失败原因和补跑命令。
