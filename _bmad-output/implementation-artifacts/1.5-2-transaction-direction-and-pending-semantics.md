# Story 1.5.2: 交易方向与 pending 口径决策

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a 产品团队,
I want 交易方向（expense/income/refund/closed）与 pending 状态聚合口径被正式决策并落地为 schema + 聚合规则,
so that Dashboard、月报、交易列表对“本月支出”的定义完全一致，避免 Epic 1 retro 指出的 Dashboard 含 pending、月报只算 confirmed、正数收入被计为支出的割裂。

## Acceptance Criteria

1. `_bmad-output/planning-artifacts/architecture.md` 必须存在并最终对齐「交易方向与状态口径」章节，明确：`direction` 枚举、`direction_confidence` 口径、`status` 口径、Dashboard / 月报 / 交易列表 / 手动记账聚合规则，以及收入/退款/关闭交易排除规则。
2. 新增 Supabase migration（下一个序号应为 `014_*`），为 `billing.transactions` 增加 `direction` 与 `direction_confidence` 字段；`direction` 取值为 `expense | income | refund | closed`，默认 `expense`；`direction_confidence` 取值为 `high | medium | low`，默认 `low`；不得改写已发布 migration。
3. migration 必须为新字段添加约束、注释和面向月度聚合的索引；既有历史交易默认 `direction = expense`、`direction_confidence = low` 以保证向后兼容，不能尝试用金额正负批量猜测历史收入。
4. 同步 `packages/shared/types/database.ts`、`packages/shared/constants/billing.ts`、`packages/shared/types/billing.ts`、`packages/shared/schemas/billing.ts`，新增交易方向与置信度的常量、类型和 Zod schema；API/mobile VO 使用 camelCase，DB 类型保持 snake_case。
5. CSV 解析和导入链路必须写入方向字段：明确支出写 `expense`、收入写 `income`、已完成退款/退还写 `refund`，无法判定时写 `expense + low` 并保持 `pending_confirmation`；失败、关闭、取消、待支付等非入账记录继续不导入。
6. `amount_cents` 保持现金流符号兼容现有数据；新聚合逻辑不得再用正负号判断支出，而必须以 `direction = expense` 为唯一支出口径，并用 `abs(amount_cents)` 计算支出金额。
7. Dashboard 月度概览必须按新口径调整：`totalExpenseCents` 表示 confirmed + expense 的本月支出；另返回 pending expense 的金额与数量（例如 `pendingConfirmationExpenseCents` + 既有/扩展 count 字段）；`income/refund/closed/rejected` 不进入本月支出。
8. 月报聚合必须按新口径调整：默认只统计 `status = confirmed AND direction = expense`；支持 `includePending=true` 查询以纳入 `pending_confirmation AND direction = expense`，供 Story 1.5.6 的“含待确认”开关复用；默认响应不得包含 pending。
9. 交易列表/最近交易契约必须返回 `direction` 与 `directionConfidence`，默认展示 `confirmed + pending_confirmation` 且排除 `rejected`；不得把收入、退款、关闭交易从流水中删除，只有“支出聚合”排除它们。
10. 若继续使用 `analytics.monthly_summaries` 预聚合，必须证明其生产口径已更新为相同的 direction/status 规则；否则本 Story 中 Dashboard/月报接口应以 `billing.transactions` live aggregate 为事实来源，避免旧预聚合污染结果。
11. Dashboard、月报、CSV parser/import service、shared schema 必须补充单元测试，覆盖：正数收入不计支出、退款不计支出、closed 不计支出、pending 默认不进月报但可通过 includePending 纳入、Dashboard 分开展示 confirmed 与 pending、历史默认 direction 兼容。
12. 验证需至少运行 story 范围测试、`pnpm test` 与 `pnpm build`；若本地 Supabase 可用，还应运行 migration reset/up 与 `pnpm db:types`，并在 Dev Agent Record 记录任何环境限制。

## Dev Notes

### 关键决策

- 本 Story 的核心不是“再修一个报表 bug”，而是把交易事实模型补完整：金额表示数值，`direction` 表示业务含义，`status` 表示确认状态。
- `direction = expense` 是所有“本月支出”聚合的唯一入口；任何通过 `amount_cents > 0` 或 `< 0` 判断支出的代码都应被删除或封装为兼容显示逻辑。
- `pending_confirmation` 是真实但未确认的交易：Dashboard 可提醒并分开展示金额/数量，月报默认不纳入，用户显式打开“含待确认”时才纳入。
- `rejected` 不进入任何聚合；`income/refund/closed` 不进入支出聚合，但仍应作为交易事实在交易列表/详情中可见。
- 历史数据默认 `expense + low` 是兼容策略，不是事实修复。不要批量把所有正数金额改成 income；支付宝/微信导出格式差异会让这种推断误伤真实支出。

### 架构约束

- 数据库变更必须通过新 Supabase migration；禁止改写 `003_create_billing_schema.sql`、`012_harden_csv_import.sql`、`013_add_ai_classification_metadata.sql` 等已发布迁移。
- API 响应继续使用 `{ success: boolean, data?: T, error?: { code: string, message: string } }`。
- 金额继续使用整数分，所有聚合使用整数运算；展示层才 `/100`。
- 日期仍按 UTC 存储与查询；月边界沿用现有 `getUtcMonthRange()` / UTC 月份策略。
- DB 字段 snake_case，API/mobile VO camelCase；mapper/服务层负责转换。
- `packages/shared` 只能放纯 TypeScript 常量、类型、schema 和工具，不能引入 React、Next、Expo 或 Node-only 依赖。
- 不新增图表、分享、预算、手动记账 UI；本 Story 的 UI 影响限于现有 Dashboard/月报字段契约和后续 Story 可复用的数据口径。

### 现有代码上下文

- `billing.transactions` 当前已有 `amount_cents`、`status`、`category_id`、`source`、`merchant`、`description`、`transaction_at`、AI 分类元数据、CSV 去重字段；缺少 `direction` 与 `direction_confidence`。
- `apps/api/lib/billing/csv-parser.ts` 当前会把“支出”转负数、“收入”转正数，并将“退款/退还/关闭/取消”等状态列入非导入关键字；本 Story 需要把已完成退款从“失败行”改为 `refund` 交易。
- `apps/api/lib/dashboard/dashboard-service.ts` 当前通过 `shouldTreatPositiveAmountsAsExpenses()` 猜测正数是否为支出，这是 Epic 1 retro 指出的 bug 来源。
- `apps/api/lib/analytics/monthly-summary-service.ts` 当前 live 查询实际使用 `status in ('pending_confirmation', 'confirmed')`，与 Story 1.7 文档“只统计 confirmed”的约束不一致；本 Story 必须修正。
- `analytics.monthly_summaries` 当前没有 status/direction/inclusion metadata。若使用旧预聚合，容易把旧口径继续带入 Dashboard/月报。
- `GET /api/billing/transactions` 当前最近交易契约未返回 direction；Story 2.1 交易列表会依赖本 Story 输出。

### Latest Technical Information

- Supabase 官方文档建议通过 `supabase/migrations` 管理 schema 变化，并用 `supabase db reset` / `supabase migration up` 在本地验证迁移；本项目仍以手写 SQL migration 为准。[Source: Supabase Local Development with schema migrations](https://supabase.com/docs/guides/cli/local-development)
- Supabase CLI `supabase gen types` 会从本地或远程数据库 schema 生成类型，并能反映表、关系、约束和自定义类型；迁移后必须同步 `packages/shared/types/database.ts`。[Source: Supabase CLI Reference](https://supabase.com/docs/reference/cli/getting-started)
- PostgreSQL enum 适合稳定的小型值集；可以新增/重命名值，但不能移除已有值或重排顺序，除非 drop/recreate。因此如果使用 enum，`expense/income/refund/closed` 与 `high/medium/low` 应视为长期契约。[Source: PostgreSQL Enumerated Types](https://www.postgresql.org/docs/current/static/datatype-enum.html)
